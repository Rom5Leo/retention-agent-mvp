Cancellation Retention Agent — MVP spec & system design

Translating a subscription platform’s ambitious, unorganized wishlist into a lean, buildable MVP: what ships, how it flows, what keeps it safe, and how it was built.

Core thesis

The client asked us to let an AI agent move money and answer anything. This design keeps the AI agent as an advisor that reasons and explains, and makes a deterministic backend the source of truth for every state change. The customer still gets an instant in-chat offer, while the highest-impact risks — unauthorized billing changes and unbounded answers — are reduced by moving authority out of the AI agent.

Deliverable 1

Scope definition — build vs. cut

The client’s run-on wishlist breaks into 11 atomic features. Each is kept, constrained, deferred, or cut — the judgment is in how the valuable-but-risky ones are reshaped rather than deleted.

  • In ships as-is
  • Constrained ships, redesigned to be safe
  • Deferred fast-follow, not needed for MVP
  • Cut out of scope
Feature (from the brief)DecisionMVP form — what ships, what’s deferred / cutWhy
1 · Trigger on “Cancel Subscription” In Intercept the authenticated cancel intent and open a retention session. The entry point; no risk.
2 · Retention conversation In Short AI chat to understand why they’re leaving. Advisory only. The core retention value.
3 · Extract churn reason In Real-time inference into predefined categories; drives the save attempt. Needed to personalize the offer; low risk as an advisory signal.
4 · Personalized discounts / plan changes Constrained Selection from an approved discount catalog (offer_id) only. Deferred custom plan adjustments (proration, commitments, bundles). Free-form “personalized” pricing invites invented offers; plan changes add billing complexity the core journey doesn’t need.
5 · Auto-update billing in real-time Constrained AI proposes an offer_id; the backend authorizes and executes a single billing op; explicit user confirm; caps, idempotency, audit; above-cap / exception → human. An AI agent must never hold financial write authority. The client’s goal (instant in-chat offer) stays; the naïve mechanism is replaced.
6 · Collect feedback In Optional, non-blocking structured questionnaire on the cancellation path. Cheap and valuable; must never block cancellation.
7 · Sentiment analysis Recast Deterministic categorization + a self-reported satisfaction/effort rating. Deferred NLP sentiment on free text. Replace an ML model with deterministic instrumentation — no training data, drift, or misclassification risk.
8 · Update CRM In Deterministic write of outcome, reason, and rating; every outcome logged for BI. Standard, low-risk system of record.
9 · Confirmation email In Deterministic templated email, sent only after a backend-confirmed cancellation. Standard; timing gated on confirmation, not on a click.
10 · Alert support on Slack Constrained Alert only on meaningful, recoverable events (handoff, high-value CRM flag, or an addressable negative signal that has an owner + action). Cut alert-on-every-cancellation. Alerting on everything is fatigue; a plain cancellation is a silent BI event.
11 · Answer any question (billing / security / tech) Constrained + Cut Bounded RAG over a small approved FAQ, retention-relevant topics only, cited, source-support gated, read-only. Cut AI-led account-security support (→ official recovery link). Deferred account-specific billing answers. Out a general “ask-anything” assistant (a separate product). “Any” means unbounded generation plus prompt-injection and social-engineering risk. Narrow it to what serves the retention conversation.

Assumptions & fallbacks

  • A1 — Billing API. The platform already exposes a billing API supporting the selected discount operation. If false → defer automated billing entirely; the AI recommends and a human / the existing flow executes.
  • A2 — Support coverage. An existing support/retention team can receive escalations. If false → defer only exception handling; approved automated discounts still run, and cancellation stays available.
  • A3 — Authentication. The user is authenticated as the account holder at cancel (in-app, logged in). Does not relax the security-Q&A cut — being logged in doesn’t make an AI agent a safe security channel.
  • A4 — Knowledge base. If no maintained approved KB exists, a small curated FAQ is the MVP plan — a content prerequisite approved before launch, not a knowledge-base-construction dependency.

Deferred to a fast-follow

Parked deliberately — valuable, but not needed to prove the MVP, and each carries real added cost. Sequenced after launch.

  • Deferred  Custom plan adjustments — proration, commitments, bundles. From feature 4; adds billing complexity beyond a single discount operation.
  • Deferred  NLP sentiment on free text — beyond the deterministic rating. From feature 7; adds an ML model with drift risk for marginal MVP value.
  • Deferred  Account-specific billing Q&A — answers from the user’s own records. From feature 11; needs authenticated retrieval, billing-state interpretation, and freshness.

The journey, step by step

StepUser / system actionAI role — reason & explain onlyOutput / state change
1 · Start Authenticated user clicks “Cancel Subscription.” Backend loads the minimum account context and the set of eligible approved offers. None. Retention session opened; subscription unchanged.
2 · Offer help Short retention conversation with a visible “Continue cancellation” option at all times. Ask why the user is leaving; infer a predefined churn-reason category; brief clarification if needed. Provisional reason recorded; user may skip.
3 · Select Determine whether an eligible approved discount addresses the reason. Exception requests, or a special-handling flag checked deterministically by the backend, branch to human handoff. Recommend an offer_id from eligible options; detect exception requests expressed in conversation; cannot invent terms. Offer proposed, handoff requested, or — if no eligible offer — continue cancellation.
4 · Terms Backend validates eligibility and supplies the exact discount terms for display. May explain the validated offer. User accepts, declines, or continues cancellation.
5 · Apply Backend re-validates and performs the single supported billing operation, with idempotency and audit logging. No authorization or execution authority. On backend-confirmed success: discount applied, subscription retained. On failure/uncertainty: pending + verify — do not claim success.
6 · Cancel If the user chooses cancellation at any point, run the existing deterministic flow, including required explicit confirmation. Cannot block or override the choice. Confirmed only on backend confirmation; effective date recorded; scheduled vs. immediate distinguished; pending/verify on API failure.
7 · Feedback Present predefined reason categories, a self-reported satisfaction/effort rating, and optional free text. Submission not required. None required. Structured feedback captured if submitted; free text stored for review.

The four lenses at a glance

Triggers & ingestion

  • Authenticated “Cancel Subscription” click is the only entry point.
  • Backend ingests minimum account context + the pre-computed eligible offer set — the AI is handed eligibility, it never derives it.

AI decision points & actions

  • Infer the churn-reason category (advisory).
  • Decide whether to attempt a save & pick the best-fit offer_id from the eligible set.
  • Detect an exception request expressed in chat (the CRM flag is checked deterministically by the backend, not the AI).
  • Answer or deflect a Q&A question via the source-support gate.
  • Explain validated offer terms.

Human-in-the-loop (HITL) handoffs

  • Runtime: exception / special-handling handoff to a specialist, with a context bundle (reason, offer shown, response, min. context, suggested next action). Non-blocking; a handoff is not a save.
  • Governance: humans approve the offer catalog and the FAQ before launch.

Outputs & state changes

  • Terminal states: Retained · Cancelled-scheduled · Cancelled-immediate.
  • Open (non-terminal): Handoff-pending.
  • Async: CRM/BI (every outcome) · email (confirmed cancellation only) · Slack (handoff or escalation, deduplicated).

Invariants the whole map obeys

  • ContainmentThe AI reasons, recommends, and explains. It never authorizes or executes a state change — the backend does, and re-derives authority independently.
  • Source of truthWhether an offer applied — or a cancellation took effect — is decided by backend confirmation, not by a click or the AI’s belief that it went through.
  • OrderingSerialize account mutations and reconcile pending operations, so a delayed discount write cannot override a confirmed cancellation.
  • Non-blockingRetention, feedback, and the human handoff are all optional. Cancellation is reachable at every step — a compliance line, not a courtesy.
  • IdempotencyDeduplicate each logical operation/event — not one write per session. Accepting a discount and later cancelling are two legitimate operations.
  • Fail safeEvery failure degrades toward the safe outcome — deflect, verify, or return to the standard cancellation flow (which still needs explicit confirmation) — rather than toward an unverified action.

Deliverable 3

Guardrails & failure matrix

Three strict guardrails — one economic, one security, one user-control — each stated as rule → enforcement point → on violation. An enforcement point shows where a control operates, not proof it can’t be evaded; residual risks are named where they remain. Reliability controls live in the failure matrix below, where they fit naturally.

Guardrail 1

Authorized offers & billing changes

Economic
Rule
The AI may only propose an approved offer_id within published caps. It never sets prices, amounts, or terms, and never invents an exception.
Enforcement
The backend independently re-checks eligibility and caps server-side keyed on (offer_id, customer), supplies the exact terms, requires explicit user acceptance, and revalidates before the single committing write (idempotent, audited). The AI agent holds no billing-write tool.
On violation
An ineligible, above-cap, or absent offer_id → refuse the write and log it; above-cap or exception requests route to a specialist. No mutation occurs on an unauthorized proposal.
Residual
Backend permission enforcement (server-side re-authorization; the AI agent holds no billing-write tool) strongly reduces the risk of unauthorized billing changes. The remaining risk is operational — a catalog/cap misconfiguration or a backend bug — not the AI agent inventing a charge.
Guardrail 2

Bounded answers & AI permissions

Security
Rule
Q&A answers only allowed retention/cancellation topics that approved FAQ content directly supports, with citations; otherwise it deflects. The AI holds no mutation tools and no access to private billing records. Conversation text and retrieved content cannot override backend policy.
Enforcement
Source-support gate (allowed topic and approved content actually supports the answer, else deflect); tool-permission isolation (a read-only retrieval tool; the offer path runs its own independent checks regardless of chat or retrieved text); security topics → a fixed official recovery link.
On violation
Unsupported, out-of-scope, or conflicting → deflect to a human or the help center. An injection attempt cannot by itself trigger an action, because authority is re-derived server-side rather than read from the conversation.
Residual
Tool-permission enforcement (no mutation tools, no billing-record access) is a hard boundary that reduces injection and data-exposure risk. Answer grounding is fallible, though — a cited passage can still be misread — so this is risk reduction, not a guarantee; the design biases toward deflection and a human route over a confident guess.
Guardrail 3

User control over cancellation

User-control
Rule
Retention, feedback, and specialist follow-up are all optional. An explicit cancellation choice bypasses further offers. Only a user-confirmed, backend-confirmed cancellation is reported complete.
Enforcement
“Continue cancellation” is reachable at every step and routes to the existing deterministic flow with explicit confirmation; the AI cannot block or override it; a pending handoff never gates cancellation; success is reported only on backend confirmation.
On violation
Any attempt — by the AI or the flow — to withhold or delay cancellation is a defect; the standard flow stays the escape hatch. A click or a timeout is never treated as a confirmed cancellation.
Residual
Protects user autonomy and click-to-cancel compliance; the remaining risk is process (a specialist not following up), handled by the F3 operational-follow-up path, not by trapping the user.

Failure matrix

ScenarioWhereGraceful handling
F1 · Mutation failure or uncertain status (discount apply or cancellation) Steps 5 & 6 Enter a pending state and reconcile the true status out-of-band; deduplicate the logical operation; keep mutations ordered so a late write can’t override a confirmed cancellation; never claim success on uncertainty. Cancellation stays available.
F2 · Invalid, malformed, or unsupported AI output Steps 2–3 & Q&A Reject the output; provide a safe deflection, a human route, or a return to the standard cancellation flow — which still executes only after explicit user confirmation. Never auto-cancel, and take no action on an unparseable recommendation.
F3 · Notification / integration failure (CRM, email, Slack) Async outputs Retry with backoff; after bounded retries, flag for operational follow-up; preserve the confirmed account state — never undo a completed mutation to fix a downstream notification.
